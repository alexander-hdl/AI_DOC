# Правила работы ИИ-ассистента: HDL (Verilog / SystemVerilog)

Версия 1.1 от 2026-10-24. История изменений — в конце файла.

Этот файл дополняет общие правила проекта (AI_RULES.md) для работы с RTL, тестбенчами и ограничениями ПЛИС. Общие правила действуют полностью: порядок работы, малые порции, тесты как спецификация, формат описаний тестов, документация, отчёт, пометка «Процесс проекта». Здесь — только то, что специфично для аппаратуры. Если правило есть в общем файле, здесь оно не повторяется, а уточняется.

Помни главное: код на HDL описывает схему, а не программу. Код, который правильно работает в симуляции, может синтезироваться не в ту схему, давать защёлки или терять данные на границе тактовых доменов. Твоя задача — не только чтобы тесты прошли, но и чтобы получилась та схема, которая задумана.

## 1. Порядок работы (дополнения к общим правилам)

1. **Сначала схема, потом код.** В плане до написания кода опиши структуру: регистры, мультиплексоры, автоматы, пути данных, тактовые домены, задержку в тактах. Для нетривиального модуля дай текстовую схему или диаграмму. Код пишется по утверждённой схеме.
2. **Интерфейс фиксируется до реализации:** порты, разрядности, домены, протокол (valid/ready, строб и т. п.), задержка. Изменение интерфейса существующего модуля — отдельное решение, а не побочный эффект задачи.
3. **Описания тестов** формулируются до реализации и утверждаются вместе с планом и схемой одним подтверждением, как в общих правилах. Обязательно включи поведение при сбросе, при обратном давлении (backpressure) и на границах разрядностей.

## 2. Синтезируемость и стиль RTL

- Строго раздели RTL и тестбенчи. В RTL запрещены: задержки `#`, `$monitor`, `force`/`release`, `initial` (кроме инициализации памяти из файла, если это явно поддерживается целевой ПЛИС и разрешено в контексте проекта), любые конструкции, работающие только в симуляции.
  - Отладочные `$display`/`$error` в RTL допустимы только внутри `` `ifndef SYNTHESIS `` … `` `endif `` и только для диагностики нарушений протокола. Логика внутри такого блока не должна влиять на схему.
- Инициализаторы в объявлениях регистров (`reg [7:0] x = 8'd0`) синтезируются на ПЛИС и подменяют сброс. Используй их только если это разрешено стратегией сброса в контексте проекта. Иначе начальное значение задаётся сбросом, а не объявлением.
- В последовательных блоках — только неблокирующие присваивания `<=`. В комбинационных — только блокирующие `=`. Никогда не смешивай их в одном блоке.
- Комбинационные блоки: `always @(*)` (или `always_comb` в SystemVerilog). В начале блока — значения по умолчанию для всех выходов блока, в каждом `case` — ветка `default`. Цель — ни одной защёлки.
- Запрещены источники расхождения симуляции и синтеза: `always_latch`, `casex`, прагмы `full_case` и `parallel_case`, значения `x` и `?` в элементах `case` (кроме `casez` для приоритетных декодеров с комментарием, почему порядок ветвей верен).
- Последовательные блоки: `always @(posedge clk ...)` (или `always_ff`). Один такт на блок.
- В начале каждого файла — `` `default_nettype none ``, в конце — `` `default_nettype wire ``.
- Явная разрядность у всех констант: `8'd5`, `4'b1010`, а не `5`. Разрядности задаются через `parameter`/`localparam` и `$clog2`, без магических чисел.
- Параметры проверяются в самом модуле: для каждого ограничения на параметр (степень двойки, диапазон, соотношение разрядностей) ставится `generate if (...) $error(...)` или `initial assert` под `` `ifndef SYNTHESIS ``, а допустимые диапазоны повторяются в README (раздел 7).
- Следи за знаковостью (`signed`) и усечением: при присваивании в более узкий сигнал явно выбирай биты и комментируй, почему усечение безопасно.
- Один модуль на файл, имя файла совпадает с именем модуля.
- Порты в стиле ANSI. Экземпляры подключаются только по именам (`.data_in(data_in)`), никогда по позиции. Неиспользуемые выходы подключаются явно пустыми скобками с комментарием.
- Соглашения об именах:
  - активный низкий уровень — суффикс `_n` (`rst_n`, `cs_n`); суффикс `_n` никогда не означает «следующее значение», для этого есть `_d`;
  - такты и сбросы — префиксы `clk_` / `rst_` с именем домена (`clk_sys`, `clk_adc`);
  - регистры и их следующее значение — `<имя>_q` / `<имя>_d` (или принятый в проекте вариант);
  - параметры и `localparam` — заглавными;
  - сигналы, пересекающие домен, — с префиксом или суффиксом, указывающим исходный домен (например, `adc2sys_`).
- Запоминающие устройства (BRAM, распределённая память, DSP) описывай по шаблонам вывода (inference templates) из документации toolchain. Если используешь примитив производителя напрямую — укажи в комментарии ссылку на раздел документации.

## 3. Такты, сбросы, тактовые домены

- Следуй стратегии сброса, зафиксированной в контексте проекта. Не выбирай её сам. Если для конкретного регистра сброс не нужен (например, конвейер данных с отдельным valid), укажи это комментарием.
- Запрещено: стробирование тактов логикой, формирование тактов из логики (кроме выделенных примитивов PLL/MMCM/делителей производителя), использование такта как данных, комбинационные петли, асинхронная логика вне утверждённых модулей.
- Вместо стробирования такта используй сигнал разрешения (enable).
- **Любое пересечение тактовых доменов — только через утверждённые модули из библиотеки CDC проекта:**
  - одиночный уровень — двухтриггерный (или трёхтриггерный) синхронизатор;
  - одиночный импульс — синхронизатор импульса (toggle + синхронизатор + детектор фронта);
  - многобитные данные — рукопожатие или асинхронный FIFO;
  - счётчики и указатели — код Грея. Код Грея безопасен только для счётчиков, которые меняются не более чем на единицу за такт (указатели FIFO). Счётчик с произвольным шагом или с загрузкой значения передаётся через рукопожатие.
- Никогда не пропускай многобитную шину через двухтриггерный синхронизатор поразрядно. Единственное исключение — квазистатические сигналы конфигурации, которые меняются только при остановленном приёмнике; такое исключение оформляется ADR и помечается в коде.
- Каждое пересечение домена помечай в коде комментарием `// CDC: <из домена> -> <в домен>, <механизм>` и отражай в карте доменов в README модуля.
- Сброс, приходящий в домен асинхронно, снимается синхронно (синхронизатор снятия сброса).

## 4. Автоматы состояний

- Состояния — именованные `localparam` (Verilog) или `enum` (SystemVerilog). Никаких числовых констант состояний в коде.
- Стиль описания — единый для проекта (см. контекст).
- Из любого недопустимого состояния автомат переходит в безопасное (обычно — в состояние сброса). Ветка `default` обязательна, но сама по себе этого не гарантирует: при извлечении автомата синтезатор перекодирует состояния и выбрасывает недостижимую ветку. Поэтому у регистра состояния ставится атрибут безопасного автомата из контекста проекта (например, `(* fsm_safe_state = "reset_state" *)` для Vivado), а в отчёте синтеза проверяется, что автомат извлечён и восстановление сохранено.
- Выходы автомата, идущие за пределы модуля, по возможности регистровые. Если выход комбинационный — укажи это в таблице интерфейса.
- Для каждого автомата в README модуля есть диаграмма состояний (Mermaid `stateDiagram` или аналог) с условиями переходов.

## 5. Верификация

- Только самопроверяющиеся тестбенчи: результат теста — «прошёл / не прошёл» с сообщением, что именно не совпало. Просмотр временных диаграмм глазами тестом не считается.
- Эталонная модель пишется отдельно от RTL (на Python в cocotb или поведенческая модель в тестбенче). Ожидаемые значения не берутся из самого RTL.
- Набор тестов включает:
  - направленные тесты на каждую утверждённую формулировку случая;
  - поведение при сбросе (в том числе сброс посреди операции);
  - граничные значения разрядностей (0, максимум, переполнение, знаковые границы);
  - обратное давление: приёмник не готов произвольное число тактов;
  - случайные тесты с фиксацией seed в логе, чтобы падение воспроизводилось.
- Инварианты протоколов проверяются утверждениями. Пример для valid/ready: пока `valid && !ready`, данные и `valid` не меняются. Форма зависит от симулятора из контекста проекта: SVA, если симулятор их поддерживает (Questa, Verilator с `--assert` для подмножества), иначе проверка в cocotb. Icarus SVA не поддерживает: для него инварианты пишутся только в cocotb.
- Каждое ожидание в тестбенче (`await RisingEdge`, ожидание `ready`, ожидание ответа) ограничено таймаутом (`with_timeout` в cocotb или счётчик тактов). Тест, который может зависнуть, не принимается.
- Verilator — двухуровневый симулятор, он не моделирует `x`. Тест, прошедший в Verilator, не доказывает, что регистры инициализированы. Если проект использует Verilator, хотя бы прогон тестов сброса выполняется в четырёхуровневом симуляторе (Icarus, Questa) или включается `--x-assign unique --x-initial unique` с разными seed.
- Для автоматов — покрытие всех состояний и переходов; непокрытые переходы перечисляются в отчёте.
- Для модулей с несколькими доменами — тесты с разными соотношениями частот и фаз тактов.
- Имена тестов описывают поведение: `test_fifo_full_blocks_write`, а не `test3`.
- Линт (Verilator `--lint-only -Wall` или принятый в проекте) проходит без предупреждений. Подавление предупреждения допускается только локально, с комментарием о причине.

### Описание тестов и утверждений

Формат описания теста, форматы ID и требования, значения поля «Вид» — общие для проекта (AI_RULES.md, «Описание тестов»). Для HDL меняется список уровней и добавляются поля.

Тест cocotb. Маркеров pytest в cocotb нет, поэтому ID и требование пишутся в docstring:

```python
@cocotb.test()
async def test_fifo_full_blocks_write(dut):
    """
    ID: FIFO-005
    Требование: REQ-FIFO-002
    Дано: асинхронное FIFO заполнено до DEPTH
    Когда: подаётся wr_en=1 на один такт clk_wr
    Тогда: full=1, данные не записываются, счётчик заполнения не меняется
    Вид: направленный
    Уровень: RTL-симуляция
    Домены: clk_wr = 100 МГц, clk_rd = 33 МГц, сдвиг фазы 0 и 90°
    """
```

Утверждение (SVA или проверка в cocotb) — это тоже тест, вида «инвариант», с ID вида `<МОДУЛЬ>-INV-<NNN>`. Описание ставится комментарием непосредственно перед утверждением, а метка утверждения совпадает с ID в нижнем регистре, дефисы заменены на подчёркивания:

```systemverilog
// ID: AXIS-INV-001
// Требование: REQ-BUS-003
// Инвариант: пока valid && !ready, data и valid не меняются
// Уровень: RTL-симуляция, формальная проверка
axis_inv_001: assert property (@(posedge clk) disable iff (!rst_n)
    (valid && !ready) |=> (valid && $stable(data)));
```

Поля, которые HDL меняет или добавляет:

- **Уровень** — `RTL-симуляция`, `симуляция после синтеза`, `формальная проверка`, `на плате`, `на стенде`. Этот список заменяет общий. Уровень «формальная проверка» допустим только если инструмент назван в контексте проекта.
- **Домены** — какие тактовые домены и соотношения частот задействованы. Для модулей с несколькими доменами перечисляются все домены и все проверенные соотношения частот и фаз.
- **Seed** — для случайных тестов число прогонов в описании, каждый seed в логе и в отчёте.

Правила:

- Каждое утверждение имеет ID и описание; в отчёте для него указывается, проверялось ли оно и сколько раз сработало его условие (что инвариант не «пустой»).
- Покрытие автоматов (состояния и переходы) и покрытие пересечений доменов собираются при прогоне и попадают в отчёт. Непокрытые переходы перечисляются явно.
- Для упавшего теста сохраняются файл временной диаграммы (VCD/FST) и seed; отчёт содержит ссылку на диаграмму и команду воспроизведения.
- Для протокольных тестов ключевой сценарий записывается в WaveDrom (из сигналов, снятых в тесте) и встраивается в документацию рядом с описанием теста.

**Процесс проекта:** cocotb пишет JUnit XML штатно (`results.xml`), ID и требование сборщик берёт из docstring по имени теста. Правила CI те же, что в общем файле, и распространяются на утверждения. В таблице «Что проверено» для HDL есть столбец «Уровень», чтобы было видно, что проверено только в симуляции, а что на железе.

## 6. Ограничения и синтез

- Файл ограничений (SDC/XDC/аналог) — часть изменения. Новый такт, новый внешний интерфейс или новое пересечение доменов без соответствующих ограничений не принимаются.
- Каждое исключение (`set_false_path`, `set_multicycle_path`, `set_max_delay` и т. п.) сопровождается комментарием: почему оно корректно и на какой модуль CDC или протокол опирается.
- Изменение принимается только при:
  - выполненных временных ограничениях (без отрицательного запаса);
  - чистом отчёте синтеза: нет защёлок, неожиданного усечения, неподключённых портов, логики, удалённой оптимизатором без объяснения.
- Сгенерированные файлы в HDL-проекте — это IP-ядра (`.xci`, `.qsys` и т. п.), обёртки IP и карты регистров. На них действует общее правило: не править руками, менять исходное описание и запускать генератор.
- Карта регистров генерируется из единого описания (генератор назван в контексте проекта) одновременно для RTL и для заголовков C прошивки. Ручное дублирование адресов и полей в RTL или в C запрещено.

## 7. Документация модуля

README модуля, помимо общего шаблона, содержит:

- **Таблицу интерфейса:** порт, направление, разрядность, тактовый домен, описание, регистровый / комбинационный выход.
- **Параметры** модуля с допустимыми диапазонами.
- **Временные диаграммы протоколов** в WaveDrom (текстом рядом с кодом).
- **Задержку** в тактах от входа до выхода и **пропускную способность**.
- **Карту тактовых доменов** со всеми пересечениями и механизмами CDC.
- **Диаграммы автоматов состояний.**
- **Ориентировочные ресурсы** (LUT, триггеры, BRAM, DSP) на целевой ПЛИС.
- **Что проверено** — генерируемая таблица тестов и утверждений модуля: ID, что проверяет, требование, вид, уровень, статус (см. раздел 5).

Значимые решения (стратегия сброса, выбор механизма CDC, формат протокола, отказ от очевидного варианта) оформляются ADR.

## 8. Режим «Обучение» для HDL

В дополнение к общим правилам режима «Обучение»:

- Прежде чем писать или разбирать код, попроси джуниора нарисовать схему: регистры, мультиплексоры, пути данных, такты. Обсуждай схему, а не синтаксис.
- При разборе кода переводи его в схему: «этот блок — регистр с разрешением», «этот `if` без `else` в комбинационном блоке даст защёлку».
- Если видишь, что код написан «как программа на C» (последовательная логика вместо параллельной, циклы как в ПО, ожидание событий), объясни разницу на конкретном примере из его кода.
- При отладке предлагай, какие сигналы вывести на временную диаграмму и что на ней искать, а не готовое исправление.

## 9. Дополнения к отчёту

Короткая и полная формы отчёта определены в общих правилах. Для HDL правка считается мелкой только если она не трогает порты, тактовые домены, автоматы и ограничения. В полной форме к отчёту из общих правил добавь:

**Изменения интерфейса и задержки** — изменились ли порты, протокол, задержка в тактах, пропускная способность.

**Тактовые домены** — появились ли новые пересечения и через какие модули CDC они сделаны.

**Ресурсы** — оценка влияния на LUT, триггеры, BRAM, DSP.

**Что реально запускалось** — расширяет одноимённый пункт общего отчёта: линт, симуляция (какой симулятор, какие тесты, сколько seed), синтез, размещение и трассировка, проверка временных ограничений. По каждому «запускал / не запускал» с результатом. Не пиши, что синтез или временные ограничения в порядке, если ты их не запускал.

**Примитивы и IP производителя** — какие использованы и что нужно сверить с документацией вендора. Ты можешь ошибаться в именах портов, параметрах и поведении примитивов конкретного производителя.

**Самопроверка по HDL-чек-листу** — по каждому пункту: «да», «нет» (с причиной) или «не применимо»:
- RTL не содержит конструкций только для симуляции (отладочный вывод только под `` `ifndef SYNTHESIS ``)
- `<=` только в последовательных, `=` только в комбинационных блоках
- Нет защёлок: значения по умолчанию и `default` во всех `case`
- Нет `always_latch`, `casex`, прагм `full_case` / `parallel_case`
- `` `default_nettype none `` в каждом файле
- Явные разрядности констант, усечения прокомментированы
- Ограничения на параметры проверяются в модуле
- Подключение экземпляров по именам
- Сброс соответствует стратегии проекта, инициализаторы в объявлениях только если разрешены
- Нет стробированных тактов и комбинационных петель
- Все пересечения доменов через утверждённые модули CDC и помечены
- У автоматов есть выход из недопустимых состояний и атрибут безопасного автомата
- Тестбенч самопроверяющийся, эталон независим от RTL
- Каждое ожидание в тестбенче ограничено таймаутом
- У каждого теста и утверждения есть ID, требование, описание, вид, уровень и домены
- Покрытие автоматов и пересечений доменов собрано, непокрытое перечислено
- Проверены сброс, границы разрядностей и обратное давление
- Линт без предупреждений
- Ограничения обновлены, исключения прокомментированы
- Сгенерированные файлы не правились руками
- README: интерфейс, WaveDrom, задержка, карта доменов, автоматы

## 10. Чего не делать никогда

- Не подгоняй тест или эталонную модель под поведение RTL, если RTL расходится с требованием.
- Не добавляй исключения временного анализа, чтобы «закрыть тайминг», без объяснения, почему путь действительно не критичен.
- Не подавляй предупреждения линта и синтеза без локального комментария с причиной.
- Не изобретай собственный синхронизатор или асинхронный FIFO, если в библиотеке проекта есть утверждённый.
- Не используй примитивы производителя по памяти без указания, что их нужно сверить с документацией.
